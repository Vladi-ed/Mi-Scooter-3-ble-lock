# Протокол Mi3 BLE

Документ описывает текущую реализацию. Аппаратные ограничения перечислены
в [README](../README.md); поддержка протокола в коде сама по себе
не подтверждает совместимость с конкретной моделью или прошивкой.

## BLE-транспорт

| Роль | UUID Nordic UART Service |
| --- | --- |
| Сервис | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| Запись (RX) | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` |
| Уведомления (TX) | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |

Если NUS не найден, приложение пробует `FFE0/FFE1`.
Метод записи выбирается с учётом свойств характеристики, с приоритетом
`writeValueWithResponse`. Завершение GATT-записи не означает, что
протокол самоката принял команду: нужен соответствующий ответ.

Длинные кадры по умолчанию передаются последовательно частями до 20 байт.
Каждая часть должна иметь **отдельный `ArrayBuffer` точного размера**:
`Uint8Array.from(chunk).buffer`. Представление `subarray()` может ссылаться
на буфер всего кадра и не обеспечивает эту изоляцию для нативного BLE-моста.
Пауза по умолчанию — 0 мс; в успешной аппаратной проверке использовались 40 мс.

Уведомления могут содержать часть кадра или несколько кадров. При новом
соединении нельзя использовать незавершённый кадр, характеристики или
отложенные операции предыдущего соединения. Отмена, таймаут и разрыв
должны завершать ожидающие операции, даже если GATT Promise не завершилась.

## Кадр

```text
5A A5 LEN SRC DST CMD ARG DATA[LEN] CK_LO CK_HI
```

`LEN` — длина данных. Контрольная сумма незашифрованного кадра равна
`0xFFFF XOR sum(LEN..DATA)` и записывается little-endian.
Зашифрованный кадр имеет 6-байтовый криптографический трейлер вместо
2-байтовой суммы; его общая длина — `LEN + 13`.

## Полная привязка

1. Исходный ключ: первые 16 байт `SHA1(name16 || FW16)`. Имя — реальные
   UTF-8 байты Bluetooth-имени, дополненные нулями или усечённые до 16 байт.
   `FW16` — константа протокола из `js/crypto.js`, не персональный секрет.
2. Приложение отправляет `0x5B` со счётчиком 0.
3. Ответ содержит 16 байт свежего `bleRandom` и 14 байт серийного номера.
   Промежуточный ключ — первые 16 байт `SHA1(name16 || bleRandom16)`.
4. Сразу отправляется `0x5C` с 16 байтами `appRandom`, первый счётчик — **3**.
   При необходимости запрос повторяется каждые 500 мс с тем же `appRandom`,
   но новым счётчиком и шифротекстом.
5. После `0x5C 00` повторы прекращаются, ожидание кнопки продолжается.
   `0x5C 01` подтверждает кнопку; прямой ответ `01` без `00` также допустим.
6. Конечный ключ — первые 16 байт `SHA1(appRandom16 || bleRandom16)`.
7. Приложение отправляет `0x5D` с серийным номером. Привязка завершена
   только после ответа `0x5D 01`; лишь тогда сохраняется `appRandom`.

Флаг `0x5B 01` указывает предыдущую привязку. Он сам по себе не доказывает
конфликт с конкретным приложением и не требует сброса самоката.
Счётчик bind зависит от предшествующего обмена и не является константой.

## Повторное подключение

После свежего `0x5B` приложение находит сохранённую привязку по серийному
номеру и имени. Используются сохранённый `appRandom`, новый `bleRandom`
и новый конечный ключ; затем отправляется `0x5D` без этапа кнопки.
Успех подтверждается только `0x5D 01`.

При отказе или таймауте ключ удаляется, GATT-соединение создаётся заново
и выполняется полная привязка с кнопкой. При отмене или разрыве ключ
сохраняется для следующей попытки. Хранилище ограничено origin браузера:
переезд на другой домен не переносит привязку автоматически.

Повторное подключение без кнопки подтверждено аппаратным журналом.

## Чтение и замок

Приложение использует адрес `SRC=0x3E`, ESC — `DST=0x20`.
Для Mi 3 AES поддерживаются ответы от `SRC=0x23, DST=0x3E`:

| Действие | CMD | ARG | DATA |
| --- | --- | --- | --- |
| Ответ чтения | `0x01` | Регистр | Значение ожидаемой длины |
| Подтверждение записи | `0x02` | Регистр | `01` |
| Заблокировать (запрос записи) | `0x02` | `0x70` | `01 00` |
| Разблокировать (запрос записи) | `0x02` | `0x71` | `01 00` |

Поддерживаются также ответы ESC `0x04/0x05`. Проверка ожидаемого ответа
учитывает адреса, регистр, команду и длину, чтобы посторонний пакет
не завершал другой запрос.

`DATA=01` подтверждает приём записи и одинаково для обеих команд замка.
Регистры `0x70/0x71` — команды, а не сохранённое состояние. Текущее состояние
читается как little-endian uint16 из `0x1D`, маска `0x0002`.
После подтверждения команды состояние проверяется до трёх раз
с интервалом 200 мс между повторными чтениями. Если состояние не подтверждено,
интерфейс сообщает о принятой команде и показывает неизвестное состояние.
Маска подтверждена аппаратным журналом: `0802` при блокировке и `0800` после разблокировки.

## Очереди, восстановление чтений и KERS

Высокоуровневые операции выполняются последовательно: весь цикл статуса,
диагностики, замка или KERS занимает одну очередь. Отдельная очередь запросов
удерживает запись и соответствующий ответ. Отключение отменяет обе очереди.

Идемпотентный запрос чтения допускает до трёх отправок в пределах исходного
таймаута 2500 мс, с интервалом 700 мс после завершённой отправки. Повторы
используют один ожидаемый ответ. После окончательного таймаута новый запрос
того же регистра требует переподключения: у протокола нет идентификаторов
запросов, позволяющих отличить запоздалый ответ.

Записи автоматически не повторяются. Полностью отправленная запись KERS
может быть проверена чтением даже без ACK; успешным считается только
совпадающее значение. Запоздалые общие ACK после такого обмена игнорируются
до переподключения. Неудачная или незавершённая GATT-запись останавливает сессию.

Полученный из сохранённого разрешения браузерный дескриптор устройства
обновляется через выбор устройства. Один таймаут начального приветствия
допускает новое соединение и повтор без удаления сохранённой привязки.
Эти механизмы восстановления требуют дальнейшей аппаратной проверки.

Диагностический JSON доступен в диалоге для копирования и скачивания;
при отказе clipboard текст можно выделить вручную. Экспорт содержит только
разрешённые показатели и настройки, без идентификаторов и материала привязки.
